Lifetime ordering where clauses are already implemented in the parser,
IR, and global signature solving.

The syntax is:

    ['a,'b where 'a < 'b]

Global signature solving now validates these constraints and stores a
lifetime ordering DAG on each declaration. These DAGs use declaration-
local lifetime ids and represent the ordering relationships required by
the declaration.

The solver also already supports the two-phase edge insertion model:

    Phase 1:
        edges coming from where clauses

    Phase 2:
        edges produced by inference
        (reborrows, storage requirements, projections, etc)

Where-clause edges are inserted first and do not trigger validation
errors. Inference edges inserted afterward may trigger errors if they
conflict with the established ordering.

The remaining work is implementing the **local propagation and validation
at specialization sites**.


----------------------------------------------------------------

Goal

Whenever a global rank1 item (struct or function) is specialized into a
local rank0 instance, the stored lifetime ordering DAG from the
declaration must be instantiated into the local lifetime graph.

Example:

    declaration:
        X<'a,'b where 'a < 'b>

    specialization site:
        X['p,'q]

This must insert the constraint:

        'p < 'q

into the local lifetime graph.


----------------------------------------------------------------

Specialization rules

Declaration lifetime ids must never be inserted directly into the local
graph.

Instead, each declaration lifetime must be remapped to the lifetime id
used at the specialization site.

Then the edges from the declaration DAG are inserted using the remapped
ids.

All inserted edges must remain O(1) amortized so the overall lifetime
solver remains O(n).


----------------------------------------------------------------

Validation example

    X = struct['a,'b where 'a < 'b] { r: &'a &'b int }

    Y = struct['a,'b,'c where 'a < 'b] {
        x: X['a,'c],
        b: &'b int
    }

This must produce an error.

Explanation:

    X requires 'a < 'b.

    Instantiating X['a,'c] produces 'a < 'c.

    Y only declares 'a < 'b.

    Therefore Y does not satisfy the constraints required by the
    specialization of X.


----------------------------------------------------------------

Important implementation constraint

Struct declarations are solved in the global solve space, while function
bodies use a local lifetime graph.

Because of this, lifetime ids from declarations must never mix with
local lifetime ids.

Every specialization must perform an explicit remapping from declaration
lifetime ids to the lifetime ids used in the current local graph.


----------------------------------------------------------------

Remaining call sites that must enforce constraints

We must ensure that specialization inserts lifetime ordering edges in
all paths where a declaration can be instantiated.

Important cases include:

    struct field types
    struct construction
    function calls
    member method currying

Struct construction and method currying currently use slightly unusual
paths and may bypass normal specialization logic, so these paths must be
verified to ensure the ordering constraints are inserted correctly.


----------------------------------------------------------------

Required invariants

    declaration lifetime DAGs are produced during global signature solving

    specialization remaps the declaration DAG into the local lifetime graph

    all inserted edges remain O(1) amortized

    declaration lifetime ids never appear in the local graph

    specialization always inserts the required ordering edges
